# Prompt 咒語收藏盒：專案檢視紀錄

> 狀態：問題先記錄，暫不在本次變更中修正。
> 檢視日期：2026-07-14

## 目前判斷

目前專案已經能支援私人單人使用，Firebase、圖片上傳、Markdown 匯入、頁籤管理、Gemini/xAI 圖片生成與 ZIP 備份等核心功能都已具備。

當 Prompt 增加到幾百組時，最需要強化的不是立刻更換框架，而是：

1. 更快找到資料。
2. 更容易批次整理。
3. 備份內容可驗證、可還原。
4. 載入大量資料時維持穩定。

另外，使用者目前還有一批尚未匯入的既有 Prompt，數量可能也是幾百組。因此匯入功能應被視為一次性的資料遷移流程，而不只是一般的檔案上傳功能。

## 待處理問題

### 高優先

- Firestore 新增或更新失敗時，編輯抽屜仍可能關閉，造成使用者輸入內容消失。
- Storage 上傳成功後取得下載網址若失敗，儲存流程可能一直停留在載入狀態。
- 備份圖片檔名可能重複而互相覆蓋，且目前固定使用 `.jpg` 副檔名。
- 備份使用 `createdAt` 排序，缺少該欄位的舊文件可能未被包含。
- README 宣稱支援文字搜尋，但目前只有標籤篩選與排序。
- 現有測試主要是未登入 DOM smoke test，尚未涵蓋 Firebase CRUD、Storage、備份與 API 錯誤流程。
- Markdown 匯入會在 `addPrompt()` 後直接計算成功數，但 `addPrompt()` 會吞掉 Firestore 錯誤，可能產生「顯示成功、實際未寫入」的假成功報告。

### 中優先

- Firestore 與 Storage 規則目前依 Email 判斷，可評估改用固定 UID 或 custom claims。
- API Keys 儲存在 LocalStorage；私人使用可接受，但同源腳本或 XSS 仍可能讀取。
- Modal 缺少完整的 dialog 語意、焦點管理、焦點鎖定與螢幕閱讀器狀態播報。
- 頁籤拖曳主要依賴滑鼠，缺少鍵盤與觸控替代操作。
- 每次 Firestore snapshot 都重新建立所有卡片，大量資料時可能造成畫面重繪成本。
- 多個操作仍缺少更細緻的進度、取消與失敗後重試狀態。

### 低優先

- README 仍保留部分已經完成的舊技術債描述。
- `IMAGE_MODEL_STORAGE` 名稱仍保留 `gemini` 字樣，但實際也儲存 xAI 模型。
- 缺少 CI、自動化部署與 Firebase Emulator 規則測試。
- 外部 CDN script 尚未配置 Subresource Integrity。

## 幾百組 Prompt 的強化建議

### 第一階段：找得到

- 增加文字搜尋欄位，搜尋標題、所有頁籤內容、頁籤名稱與標籤。
- 搜尋結果採 debounce，避免每次按鍵都完整重繪。
- 顯示目前結果數量，例如「顯示 42 / 318 筆」。
- 保留現有標籤篩選，並明確標示多個標籤是「全部符合」還是「任一符合」。
- 增加日期、是否有圖片、頁籤數量等輕量篩選條件。

對幾百組資料來說，第一版可以在瀏覽器建立搜尋索引，不必立刻導入 Elasticsearch 或更複雜的後端搜尋服務。

### 匯入大量既有 Prompt

第一階段已完成大量匯入的主要保護，現在可以選擇多個 Markdown 或 ZIP 檔案，先解析與預覽，再確認寫入 Firestore：

- 先解析全部檔案，顯示匯入預覽與總筆數，再由使用者確認寫入。
- 在預覽中顯示檔名、標題、頁籤數、標籤與解析錯誤。
- 依檔案內容或標題加上重複檢查，避免同一批資料重複匯入。
- 每筆資料保留 `sourceFileName`、`importBatchId` 與 `importedAt`，方便追蹤與回溯。
- 依序寫入並顯示目前進度，避免一次匯入太多資料時畫面看似卡住。
- 匯入失敗時保留成功與失敗清單，並提供狀態篩選，方便後續重試。
- 匯入前先做格式驗證，避免不完整 Markdown 直接產生空白或品質不佳的 Prompt。
- 提供「取消本批匯入」或匯入後依 `importBatchId` 批次移除的復原方式。
- 匯入完成後自動產生一份匯入報告，記錄成功、重複、失敗與略過的檔案。

Virtual 專案的 ZIP 可以附帶 `manifest.json`，讓來源標籤與結構化 metadata 直接匯入，不需要呼叫 AI API。後續仍可補上依 `importBatchId` 批次移除或撤銷功能。

### 第二階段：整理得快

- 增加批次選取模式。
- 支援批次新增或移除標籤。
- 支援批次封存、刪除與恢復。
- 提供「最近更新」、「有圖片」、「未分類」、「常用」等智慧篩選。
- 允許將目前搜尋與標籤條件儲存成自訂檢視。
- 卡片可加入收藏或使用次數，讓常用 Prompt 排在前面。

### 第三階段：備份可靠

- 備份資料使用穩定的 Prompt ID 與頁籤索引組成圖片路徑，避免同名覆蓋。
- 保留原始副檔名與 MIME type。
- ZIP 增加 `manifest.json`，記錄文件數、圖片數、失敗項目與匯出版本。
- 備份完成後提供明確報告：成功幾筆、跳過幾張圖片、原因是什麼。
- 增加還原功能，先做格式驗證與預覽，再寫入 Firestore。
- 支援只備份目前搜尋結果或目前選取的 Prompt。
- 需要時再增加分批備份，避免資料與圖片量變大後造成瀏覽器記憶體壓力。

### 第四階段：大量資料穩定性

- 卡片採分頁或虛擬列表，每次只渲染有限數量。
- 圖片維持 lazy loading，並避免每次 snapshot 都清空整個卡片容器。
- Firestore 文件補上 `schemaVersion`、`variantCount`、`hasImages` 等可查詢欄位。
- 評估啟用 Firestore offline persistence，讓已載入資料在短暫斷線時仍可閱讀。
- 將 Prompt 內容與列表摘要分離，列表先載入必要欄位，編輯時再載入完整內容。

## 建議實作順序

1. 先修正儲存失敗、Storage 卡住與備份覆蓋問題。
2. 加入文字搜尋與結果數量。
3. 加入批次選取、批次標籤與封存。
4. 重做備份 manifest，加入只備份篩選結果與還原預覽。
5. 再視實際資料量加入分頁、虛擬列表與 Firestore offline persistence。
6. 最後補 Firebase Emulator、主要流程 E2E 與 CI。

## 架構判斷

以目前「個人使用、幾百組 Prompt」的規模，Vanilla JavaScript + Firebase 仍然足夠，不需要為了資料量立刻遷移到 React 或更大型後端。

真正需要先改善的是搜尋索引、批次操作、備份格式與失敗復原。等資料量接近數千組，或需要多人協作、權限分層與複雜搜尋時，再評估更完整的後端索引與前端框架會比較划算。
